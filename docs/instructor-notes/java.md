# Java 워크숍 강사 노트: Java 8에서 Java 25로 업그레이드하고 Azure에 배포하기

**핵심 질문:** “Java 8 기반 레거시 앱을 Java 25로 현대화하고, 클라우드 네이티브 앱으로 Azure에 배포하려면 무엇을 바꿔야 할까요?” 이 워크숍은 원본 앱을 평가하고 업그레이드한 뒤, Azure 서비스와 연동하는 web/worker를 Azure Container Apps(ACA)에 배포하는 전 과정을 다룹니다.

## 시작 전: 강사만 준비할 것

참가자 사전 과제는 없습니다. 강사는 개인 정보가 없는 PNG, [Java 실습 목차](../java/README.md), [문제 해결](../java/08-troubleshooting.md)을 열어 두세요. [리허설 점검표](../../CONTRIBUTING.md#instructor-rehearsal-checklist)에 따라 강사용 환경에서 원본 업로드와 배포 후 업로드를 예행연습하세요. 대기 시간에 보여줄 평가 보고서, worker 로그와 결과 화면은 비밀정보를 가린 상태로 준비합니다.

## 0. 환경 준비: 빈 기기에서 함께 시작하기

1. 참가자와 함께 OS, 설치 권한, GitHub 계정과 Copilot 라이선스, 사용할 Azure 구독을 확인하세요. 누락된 도구는 지금 설치합니다. Azure 구독 승인이 늦어져도 가능한 로컬 실습은 계속할 수 있습니다. Copilot 사용이나 설치가 조직 정책으로 막히면 강사 화면을 보도록 하고 계정을 공유하지 않습니다.
2. [준비 문서](../java/00-setup.md)에서 OS에 맞는 Copilot app, 셸과 컨테이너 엔진부터 준비합니다. Windows는 PowerShell 7, macOS와 Linux는 Bash 또는 Zsh 터미널을 사용합니다. `gh`가 없으면 먼저 설치하고 로그인한 뒤, 템플릿으로 **본인 저장소를 만들고** 복제합니다. Copilot app 세션에서 터미널을 열어 `README.md`와 `scripts/`가 보이는 워크숍 루트를 짚어 주세요.
3. 워크숍 루트에서 Java 트랙 점검을 실행합니다. `FAIL`은 필요한 항목을 참가자가 직접 승인해 설치한 뒤 다시 확인하고, `MANUAL`은 로그인, 라이선스와 권한을 직접 확인합니다. 설치를 기다리는 동안 “Azure CLI와 azd 중 한쪽에만 로그인하면 어떻게 될까요?”라고 물어 두 도구의 로그인 상태를 각각 확인하게 하세요.
4. 엔진이 응답하는지, JDK 8과 25, Modernize CLI 및 `psql`을 사용할 수 있는지 확인합니다. `Azure`와 `justinyoo-skills` 플러그인을 설치하고 Java 샘플을 내려받습니다. 한 참가자에게 **워크숍 루트**와 `pom.xml`이 있는 **앱 루트**(`java/`)를 차례로 보여 달라고 하세요. 점검의 `PASS`는 빌드나 배포 성공이 아닙니다.

## 1~2. 바꾸기 전에 기준 세우기

**원본 실행.** 참가자가 앱 루트에서 JDK 8을 선택하고 Maven Wrapper로 빌드한 뒤 원본 앱을 시작합니다. `http://localhost:8080`에서 PNG를 올리고 RabbitMQ의 `image-processing` 큐를 여세요. “Ready가 0인 이유가 처리 성공 말고도 있을까요?”라고 묻고, 참가자가 worker의 `Successfully generated thumbnail` 로그와 실제 썸네일을 **함께** 가리키도록 하세요. `dev`는 로컬 파일을 쓰며 업로드 메타데이터를 DB에 기록하지 않습니다. DB 기록은 이후 `dev`가 아닌 S3 경로와 비교합니다. 원본을 종료하고 참가자 저장소에 비교 기준이 될 원본 상태를 커밋합니다.

**평가와 계획.** 앱 루트의 Modernize CLI에서 `Assess`를 실행합니다. 보고서에서 위험 하나를 고르게 하세요. 예를 들어 “컨테이너를 교체하면 로컬 디스크의 사진은 어떻게 될까요?”라는 질문을 [워크숍 지침](../java/modernize-rulebook-source.md)과 연결합니다. `Rulebook`을 만든 뒤 `Plan`에서 보고서와 지침을 반영한 **하나의 계획**을 작성합니다. 참가자가 `plan.md`와 `tasks.json`에서 기준 테스트, 업그레이드, 연동 코드, 배포 산출물 순서를 찾고 **실제 Azure 생성과 DB 변경은 실행 범위 밖**임을 확인해야 `Execute`로 넘어갑니다. 생성이 늦으면 강사 보고서와 계획으로 이 판단을 연습하되 미검토 계획을 승인하지 않습니다.

## 3~5. 업그레이드 결과에서 배포 승인까지

| 강사가 던질 질문 | 참가자가 확인할 근거 |
| --- | --- |
| “업그레이드 전후에 같은 동작을 어떻게 비교하나요?” | JDK 8 기준 테스트에서 승인한 계획 실행을 시작합니다. 실행 후 같은 셸에서 JDK 25를 선택하고 Maven Wrapper의 버전, `clean verify`와 web/worker 모의 테스트 결과를 확인합니다. `BUILD SUCCESS`는 실제 Azure 연결 증거가 아닙니다. |
| “메시지 처리가 실패하면 업로드를 성공으로 봐도 될까요?” | RabbitMQ를 대신하는 Service Bus에서 worker가 성공한 메시지만 완료하는지 확인합니다. 파일은 로컬 디스크나 S3 대신 비공개 Blob에서 조회하고, S3 경로의 메타데이터는 PostgreSQL Flexible Server에서 기록하고 조회해야 합니다. 실제 연결용 `azure-it` 테스트는 여기서 준비만 합니다. |
| “배포를 승인하면 무엇이 생기고 누가 접근하나요?” | Dockerfile 두 개와 `azure.yaml`에서 로컬 이미지 빌드와 web/worker 분리를 찾습니다. Bicep과 훅에서 관리 ID, 역할, DB 네트워크 경로, 리전, SKU와 비용을 대조합니다. 구독이나 비용, 권한 범위가 불명확하면 프로비저닝하지 않습니다. |

**시간이 부족할 때:** 구간 안에 생성이 끝나지 않으면 진행 중인 작업부터 정상 종료합니다. 참가자가 동의한 경우 **워크숍 루트**에서 해당 실습 문서의 스냅샷 도우미를 실행하고 새 `java/`로 이동합니다. 도우미는 기존 앱을 백업하고 스냅샷으로 교체합니다. 다음 표에서 **지금 막힌 작업**에 해당하는 한 곳을 선택하세요.

| 막힌 작업 | 스냅샷 | 재개할 때 확인할 것 |
| --- | --- | --- |
| Modernize 계획 실행 | [03: 업그레이드](../java/03-upgrade.md#스냅샷-적용) | JDK 25로 다시 빌드하고 web/worker 모의 테스트 실행 |
| 연동 코드 검토와 수정 | [04-1: 서비스 이전](../java/04-migrate-azure-services.md#스냅샷-적용) | DB, 큐, Blob 처리 경로와 로컬 테스트 결과 |
| 실제 연결용 테스트 준비 | [04-2: 통합 테스트](../java/04-migrate-azure-services.md#azure-통합-테스트-준비) | `azure-it` 프로필, 별도 테스트 큐, 실행 승인 절차 |
| 배포 산출물 준비 | [05: azd 산출물](../java/05-prepare-azd.md#스냅샷-적용) | Dockerfile, `azure.yaml`, Bicep과 DB 초기화 대상 |

스냅샷은 설치나 배포를 대신하지 않습니다. 필수 검증이 실패하면 다음 변경을 실행하지 말고 [문제 해결](../java/08-troubleshooting.md)로 안내하세요. 강사 시연을 본 결과와 참가자가 직접 확인한 결과는 구분합니다.

## 6. Azure Container Apps에 직접 배포하고 검증하기

1. **프로비저닝:** 참가자가 앱 루트에서 개인별 azd 환경을 선택하거나 만들고, Azure CLI와 azd의 구독, 리전, 생성 범위와 비용을 대조해 승인한 뒤 `azd provision`을 실행합니다. 기다리는 동안 어떤 리소스가 PNG, 메시지, 메타데이터를 맡는지 짚어 보세요. 성공 후 실제 리소스 목록을 승인한 범위와 비교합니다.
2. **DB와 이미지:** 승인한 클라이언트 IP와 TLS 인증서를 확인한 뒤 **새 데모 DB만** 초기화합니다. 사용자를 설정한 결과와 테이블 권한을 확인하고 `azd package`로 web과 worker 이미지를 로컬에서 빌드합니다. 두 이미지의 빌드가 성공한 뒤 `azd deploy`를 실행합니다. 이 과정을 `azd up` 한 번으로 대체하지 않습니다.
3. **기능 확인:** 참가자가 실제 배포된 두 수정 버전과 web의 외부 수신, worker의 수신 비활성화를 확인합니다. `azd show`의 web URL에서 원본 실습과 같은 PNG를 올립니다. “HTTP 200 말고 처리된 증거는 무엇인가요?”라고 묻고, 해당 업로드의 worker 로그, 썸네일 조회, DB 메타데이터와 비공개 Blob의 익명 접근 거부를 대조하세요. 로컬 계정으로 실행한 Azure 통합 테스트와 앱의 관리 ID로 동작한 결과는 별개입니다. [통합 및 종단 간 테스트](../java/06-deploy-aca.md#azure-통합-테스트-실행)에서 수행하지 못한 검사(새 수정 버전에서 다시 조회 등)는 미검증으로 남깁니다.

**정리 전환 시각은 기본 01:50, 연장 02:20입니다.** 배포가 늦어지면 새 배포나 재시도를 시작하지 않습니다. 진행 중인 작업 상태와 생성된 리소스부터 확인하고, 강사 결과로 남은 흐름을 설명하세요. 참가자 배포가 실패했더라도 비용이 발생하는 리소스는 남을 수 있습니다.

## 7. 정리와 마무리

각 참가자가 azd 환경, 구독, 리소스 그룹과 삭제 목록을 대조합니다. **본인 실습 대상만 있고 삭제를 승인한 경우에만** 앱 루트에서 `azd down`을 실행합니다. 전용 그룹의 삭제 여부를 확인하고, 공유 리소스가 섞였거나 소유자가 불분명하면 삭제하지 않습니다. Azure를 사용하지 않았다면 로컬 정리만 합니다. 프로비저닝에 실패했다면 포털에서도 남은 리소스를 확인하세요.

이번 실습의 로컬 web, worker와 컨테이너를 종료합니다. 수업을 마치기 전에 참가자마다 **직접 확인한 기능 하나, 아직 확인하지 못한 항목, 남은 유료 리소스와 정리 책임자**를 기록하게 하세요. 삭제 요청을 보낸 것과 삭제를 확인한 것은 구분합니다.
