# 4. Azure 서비스로 의존성 이전하기

[전체 목차](../../README.md) | [Java 목차](README.md) | [이전: 업그레이드](03-upgrade.md) | [다음: azd 준비](05-prepare-azd.md) | [문제 해결](08-troubleshooting.md)

## 목표

이전 실습에서 준비한 Azure 서비스 이전 코드와 테스트가 기존 동작을 유지하는지 검토하고, 필요한 부분을 수정해 로컬에서 검증합니다.

## 실습 범위

이 실습에서는 [실습 3: JDK 25로 업그레이드하기](03-upgrade.md)에서 준비한 Azure 서비스 이전 코드와 테스트, 빌드 및 모의 테스트 결과를 요구사항과 대조합니다. 문제가 발견되면 승인한 범위에서 수정하고 로컬 테스트를 다시 실행합니다. 실제 Azure 서비스에 연결할 통합 테스트도 준비하되 이 단계에서는 실행하지 않습니다.

| 단계 | 다루는 내용 | 이 단계에서 하지 않는 작업 |
| --- | --- | --- |
| [실습 3: JDK 25로 업그레이드하기](03-upgrade.md) | Java 업그레이드, Azure 서비스 이전 코드와 배포 산출물 준비, 로컬 빌드 및 모의 테스트 | Azure 리소스 생성, 실제 Azure 연결, 앱 배포 |
| 실습 4: 이 문서 | 이전된 Azure 서비스 코드와 테스트 검토, 필요한 수정과 로컬 검증 | Azure 리소스 생성과 실제 연결 |

### Azure 이전 대상과 보존할 동작

| 기존 의존성 | 목표 | 보존할 동작 |
| --- | --- | --- |
| PostgreSQL 컨테이너 | Azure Database for PostgreSQL Flexible Server | DB 연결과 `dev` 외 S3 경로의 메타데이터 기록 및 조회 |
| RabbitMQ | Azure Service Bus 큐 | 생산자와 소비자의 계약, 처리 결과와 오류 복구 |
| `dev`의 로컬 파일과 `dev` 외 AWS S3 | 비공개 Azure Blob Storage | 업로드 후 조회, 접근 제어와 파일 식별 |

## 실습 전 확인 사항

이전 실습의 JDK 25 빌드와 모의 테스트 결과를 확인한 뒤, 같은 Copilot app 터미널의 **앱 루트**를 계속 사용합니다.

## 코드 이전 요구사항 확인

다음 요구사항이 생성된 코드와 테스트에 반영됐는지 확인합니다.

```text
`.github/modernize/rulebook/`의 rulebook과 실제 업그레이드 결과를 읽고
Azure 서비스 이전 코드와 테스트를 검토해 줘. 파일을 변경하거나 명령을 실행하지 마.
JDK 25와 현재 Spring Boot 버전을 유지하고 web과 worker의 기존 기능을 보존하는지 확인해 줘.

- **PostgreSQL:** Flexible Server와 TLS를 사용하고, 커넥션 풀에서 관리 ID/Entra 인증과 토큰 갱신이 올바르게 동작하는지 확인해 줘.
- **Service Bus:** RabbitMQ를 대체하는 생산자와 소비자를 확인해 줘. 메시지 형식과 처리 동작을 유지하는지, 성공 시 complete, 실패 시 abandon/dead-letter를 수행하는지 검토해 줘. 중복 수신 시 멱등 처리와 종료 시 소비자 정리도 확인해 줘. worker는 장기 실행 소비자로 유지하고 KEDA는 추가하지 마.
- **Blob:** 파일을 비공개 Blob에 저장하고 인증된 서버를 통해 조회하는지 확인해 줘. 컨테이너 로컬 디스크를 영구 저장소로 쓰거나 공개 컨테이너, 무기한 SAS URL을 사용하지 마. `dev` 외 S3 경로의 코드와 설정, DB 메타데이터 기록과 조회 동작을 보존하고, `dev` 업로드 경로에 없던 DB 기록을 추가하지 마.
- **인증과 SDK:** 로컬 개발 자격 증명과 ACA 관리 ID를 구분하고, 선택한 인증 체인(예: `DefaultAzureCredential`)의 실제 동작을 설명해 줘. 비밀정보를 코드, 설정, Git에 넣지 말고 현재 Spring Boot 및 JDK 25와 호환되는 Azure SDK를 근거와 함께 확인해 줘. 호환되지 않는 Spring Cloud Azure starter는 추가하지 마.
- **문서와 테스트:** 변경된 환경 변수, 필요한 리소스와 역할, DB 초기화 절차가 문서화됐는지 확인해 줘. 단위 테스트는 Azure 없이 실행할 수 있어야 해. DB, 큐, Blob 통합 테스트는 별도로 준비하는 계획을 세워 줘.
- **제외 범위:** S3 데이터 이전이나 AWS 리소스 접근은 필요성만 검토하고 실행하지 마. 인프라 생성, 실제 DB 변경과 데이터 이전, 이미지 게시, 배포는 작업 목록에서 제외해 줘.

각 판단의 근거로 파일 경로와 줄 번호를 제시하고, 코드에서 확인할 수 없는 항목은 미확인으로 표시해 줘.
```

## 생성 결과 검토

- [ ] 위의 읽기 전용 검토 요청을 Copilot app 채팅에 보내고, 앱 코드나 Azure 리소스를 변경하지 않은 상태에서 응답에 제시된 파일 경로와 줄 번호를 확인합니다.
- [ ] 앱 루트에서 실습 3 이후의 변경을 확인합니다. `git diff`에서 앱 외부 파일, 불필요한 생성물이나 비밀정보가 포함되지 않았는지 살핍니다.

    ```text
    git status --short
    git log --oneline "$before..HEAD"
    git diff "$before"
    ```

- [ ] `infra/`의 Bicep에서 `identity`와 `Microsoft.Authorization/roleAssignments`를 찾아 `principalId`가 해당 앱의 관리 ID인지 확인합니다. web의 Service Bus Data Sender, worker의 Data Receiver, Blob의 컨테이너 범위와 역할을 확인하고, Contributor나 구독 전체 권한이 없는지 살핍니다. Bicep 파일 경로와 줄 번호를 기록하고 확인할 수 없는 권한 할당은 미확인으로 남깁니다.
- [ ] 실습 3에서 실행한 `./mvnw -pl web,worker -am verify` (PowerShell은 `./mvnw.cmd -pl web,worker -am verify`)의 터미널 결과를 확인해 단위 테스트 상태를 기록합니다. Azure 통합 테스트는 실행하지 않고 미실행으로 표시합니다.
- [ ] 각 앱의 `application*.yml` 또는 `application*.properties`와 README에서 로컬 `dev`와 Azure 설정으로 실행하는 방법을 확인합니다.
- [ ] PostgreSQL 권한과 초기화 절차는 [5. azd 배포 산출물 준비하기](05-prepare-azd.md)에서 검토하고, 실제 초기화는 [6. azd로 ACA에 배포하기](06-deploy-aca.md)에서 승인 후 수행합니다.

## 발견 사항 조치

검토 결과에 수정이나 추가 확인이 필요하면 같은 Copilot app 채팅에 다음과 같이 요청합니다.

```text
위 검토 결과를 코드 수정이 필요한 항목과 추가로 확인할 항목으로 구분해 줘.
각 항목의 근거, 영향, 수정 방법과 필요한 테스트를 제시해 줘.
실제 Azure 연결이 필요한 검증은 따로 표시해 줘.
파일을 변경하거나 명령을 실행하지 마.
```

코드 수정이 필요하면 제안된 범위를 검토한 뒤 승인한 항목을 명시하고 별도로 요청합니다.

```text
위에서 승인한 항목만 수정하고 관련 테스트와 문서를 갱신해 줘.
앱 루트에서 현재 셸에 맞는 `../scripts/`의 `use-java` 도우미로 JDK 25를 선택해 줘.
같은 셸에서 실습 3의 빌드와 web/worker 모의 테스트를 실행해 줘.
실제 Azure 연결, 리소스 생성, DB 변경과 배포는 하지 마.
변경 파일, 테스트 결과와 남은 미검증 항목을 보고해 줘.
```

수정 후 변경 범위와 테스트 결과를 살피고, 읽기 전용 검토를 다시 요청해 해결 여부를 확인합니다.

## Azure 통합 테스트 준비

DB, Service Bus와 Blob을 실제 Azure 서비스에 연결해 검증할 테스트를 준비합니다. 이 테스트는 앞서 실행한 모의 테스트와 별개입니다. Copilot app 채팅에 다음을 요청합니다.

```text
현재 앱의 Azure 서비스 코드, 테스트와 빌드 설정을 읽고 실제 Azure 연결용 통합 테스트를 작성해 줘.
기존 테스트 도구를 우선 사용하고, Azure 리소스 생성이나 실제 연결 없이 테스트 코드와 실행 안내만 준비해 줘.

- PostgreSQL의 TLS 연결과 테스트 데이터의 기록 및 조회, Blob의 비공개 저장 및 조회, Service Bus의 메시지 송수신과 처리 결과를 각각 검증해 줘.
- 실제 코드의 동작과 테스트 대상에 근거해 성공 조건을 작성해 줘. 확인할 수 없는 동작은 추측하지 말고 미검증으로 표시해 줘.
- 테스트 전용 데이터와 고유 식별자를 사용하고 기존 데이터나 메시지를 수정하거나 삭제하지 않도록 해 줘. 메시지 수신은 다른 메시지를 소비하지 않는 전용 큐에서만 수행해 줘. 자동 정리는 하지 말고 테스트 데이터와 별도 정리 방법을 안내해 줘.
- Maven의 `azure-it` 프로필로 실제 Azure 연결 테스트를 명시적으로 실행하도록 분리해 줘. 앱 루트에서 `./mvnw -Pazure-it -pl web,worker -am verify`로 실행하고, PowerShell에서는 `./mvnw.cmd`를 사용해 줘.
- 기본 빌드와 모의 테스트에서는 실제 Azure 연결 테스트가 실행되지 않게 해 줘. `azure-it` 실행 시 필수 대상이 없거나 연결에 실패하면 실패로 보고하고, 테스트가 없거나 모두 건너뛰어도 성공으로 오인하지 않게 해 줘.
- 구독, 리소스, 실행 주체, 필요한 최소 권한과 네트워크 경로, 읽기와 쓰기 범위, 환경 변수, 예상 비용을 실행 안내에 명시해 줘. 로컬 실행 주체와 배포된 앱의 관리 ID를 구분해 줘.
- 앱 루트에서 Windows PowerShell과 WSL/Linux의 Bash 및 macOS의 zsh/bash 각각으로 실행할 수 있는 정확한 준비 및 실행 명령, 결과 확인과 실패 시 조치를 제시해 줘. JDK 선택이 필요하면 해당 셸의 `../scripts/` 도우미를 사용해 줘. 값이 없는 대상은 임의로 채우지 마.
- 비밀정보를 코드, 명령 인자, 로그나 Git에 넣지 마. 의존성이나 도구의 설치가 필요하면 설치하지 말고 필요한 항목을 보고해 줘.
- 실제 Azure 연결, 데이터 변경, 배포, 테스트 실행과 도구 설치는 하지 마. 변경 파일과 검토가 필요한 항목을 보고해 줘.
```

생성된 코드와 실행 안내에서 `azure-it` 프로필과 테스트가 실제로 연결되어 있는지, 대상과 권한, 테스트 데이터 범위, 기본 빌드와의 분리, 성공 및 실패 조건을 확인합니다. 필요한 도구나 대상이 불분명하면 해결한 뒤 진행합니다. 실제 연결 테스트는 미실행으로 기록하고 [실습 6: azd로 ACA에 배포하기](06-deploy-aca.md)에서 대상과 영향을 승인한 뒤 실행합니다.
